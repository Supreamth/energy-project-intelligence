เป้าหมาย

พิสูจน์ว่าระบบรับหลักฐาน → ให้คนตรวจ → แสดงทะเบียนโครงการพร้อมที่มา ได้กับข้อมูลจริง ไม่ใช่แค่สร้างตารางสำเร็จ

MVP ที่วัดได้: เปิดโครงการหนึ่ง → เห็นบริษัท ไซต์ กำลังผลิต/โหลด สถานะ และวันที่สำคัญ → กดดูหลักฐานต้นฉบับของแต่ละค่า → เห็นค่าขัดแย้งและเหตุผลที่เลือก
ในขอบเขต MVP
  • solar_farm และ data_center ในประเทศไทย
  • ตัวอย่างจริงที่ได้รับอนุญาต 5–10 โครงการ ทั้งสองประเภท
  • หลักฐานจาก กกพ., BOI, ประกาศเจ้าของ ตามสิทธิ
  • manual upload/import ก่อน collector อัตโนมัติ
  • หน้าเว็บภายในสำหรับตรวจหลักฐานและเลือก canonical
  • internal-only ไม่เปิด public API/export
ยังไม่ทำ
  • วิเคราะห์ภาพดาวเทียม
  • Solar Portfolio และข้อมูลมิเตอร์
  • auto-merge ตัวตนที่คลุมเครือ
  • LLM อนุมัติข้อมูลเอง
  • Kubernetes หรือคิวกระจายหลายเครื่อง

ตัวตน

organization → project → site → phase → asset (asset ใช้เมื่อมี Portfolio ภายหลัง) โครงการไม่ใช่บริษัท และไม่ใช่หนึ่งเฟสเสมอไป ห้ามสร้างเฟสสมมติจากยอด MW รวม

ความหมายที่ห้ามปน

  • MWp, MWac, IT load, facility power คนละ metric
  • project total กับ phase total คนละขอบเขต
  • วันที่คาดการณ์ไม่กลายเป็นวันที่เกิดขึ้นจริง
  • สำนักงานใหญ่ไม่ใช่พิกัดไซต์
  • ก่อสร้างเสร็จภายนอกไม่เท่ากับเปิดดำเนินงาน
  • แหล่งหายหรือ HTTP 404 ไม่เท่ากับโครงการยกเลิก
  • NULL = ไม่ทราบ ห้ามใส่ 0 แทนข้อมูลหาย

Development process

ทำทีละช่วง แต่ละช่วงต้องมีผลที่ทดสอบได้ อย่าข้ามไป collector จนกว่า manual workflow จะผ่าน

  1. Observe — อ่านสถานะจริงจากเครื่อง, git, ฐานข้อมูล, เอกสารนี้ และ status.json
  2. Plan — เลือกงานที่เล็กที่สุดที่ขยับ milestone ปัจจุบัน
  3. Act — แก้เฉพาะที่จำเป็น ไม่ขยายขอบเขต
  4. Verify — รันคำสั่งจริง เก็บหลักฐาน ไม่เชื่อคำอ้างของเอเจนต์
  5. Decide — ผ่าน / ทำต่อ / บล็อก แล้วอัปเดตเอกสารนี้กับ status.json
  6. Publish docs — ทุกครั้งที่สถานะเปลี่ยน ต้องอัปเดตเว็บสด https://enerise.sprees.net/ ก่อน แล้วค่อย sync เข้า git
อย่า commit, push, deploy, ลบข้อมูล หรือแตะ secret ถ้าผู้ใช้ไม่ได้สั่ง ยกเว้นเมื่อผู้ใช้สั่งเชื่อม GitHub แล้ว ห้ามใส่รหัสผ่านใน git

Acceptance checks

อย่าอ้างว่าผ่านทั้งเอกสารใน MVP ที่ยังไม่มี imagery หรือ Portfolio

  1. ดึง snapshot เดิมซ้ำ: raw ไม่เพิ่ม, มี fetch event ใหม่
  2. record เดิมเปลี่ยน: snapshot ใหม่, evidence เก่ายังอยู่
  3. สองแหล่งบอก 40 กับ 50 MW: เก็บสอง evidence, เลือก canonical พร้อมเหตุผล
  4. 50 MWp ไม่ทับ 40 MWac และไม่รวมกับ 20 MW IT load
  5. project total ไม่ถูกนับซ้ำกับ phase total
  6. ชื่อเหมือนกันต่างจังหวัดไม่ merge; ใกล้กันต่างเฟสไม่ merge
  7. วันที่ Q4 คงเป็นช่วง
  8. ไม่พบภาพใหม่ไม่ทำให้สถานะถอยหลัง (เมื่อมี imagery)
  9. rights unknown/internal-only ไม่หลุด public
  10. Tenant isolation ทั้ง DB และ object storage (เมื่อมี Portfolio)

Guardrails

  • ห้าม LLM เติมค่าที่ไม่มีหลักฐาน
  • กรณี match คลุมเครือเข้าคิวคน ห้าม merge อัตโนมัติด้วยระยะทางอย่างเดียว
  • ingestion role ห้ามแก้ canonical โดยตรง
  • เปลี่ยน canonical โดยปิดแถวเดิมและเพิ่มแถวใหม่ใน transaction เดียว
  • เลื่อน cursor หลัง durable commit เท่านั้น
  • credential ไม่อยู่ในตาราง sources และไม่อยู่ใน git
  • object storage ของ raw เป็น private
  • อย่าเริ่มสาม connector พร้อมกัน
  • อย่า encode ความล้มเหลวชั่วคราวของเครื่องเป็นกติกาถาวรในเอกสาร
